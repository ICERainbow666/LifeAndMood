# 开发约束

本项目为合作开发项目，所有成员在提交代码前需遵守以下约束。

## 1. 分支规范

- **主线分支**（`master` / `main`）不遵循此规则，直接使用主线分支名。
- **除主线外的所有分支**必须带上个人 id，格式为 `类型/个人id/简短描述`，例如：

```
feat/a/mood-record     # a 开发心情记录功能
fix/a/pet-feed-bug     # a 修复宠物喂养 bug
refactor/a/diary       # a 重构手札模块
docs/a/db-design       # a 修改数据库设计文档
```

个人 id 由团队统一分配，同一个人在自己所有分支中使用同一个 id，方便按人识别分支归属。

分支类型共四种：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能设计与开发 |
| `fix` | Bug 修复 |
| `refactor` | 重构（不改变功能，改善代码结构） |
| `docs` | 文档修改 |

## 2. 提交类型优先级

当一轮工作包含多种类型时，按以下优先级决定提交到哪个分支：

**refactor > feat > fix > docs**

规则：

1. 本轮只做了一种类型的工作 → 提交到对应类型的分支。
2. 本轮做了多种类型的工作 → 提交到优先级最高的类型对应的分支。
3. 无论提交到哪个分支，提交信息必须**完整描述本轮做过的所有工作**，不能只写优先级最高的那一种。

### 示例

本轮先完成了一次重构，之后又开发了一个新功能：

- 提交分支：`refactor/a/...`（refactor 优先级高于 feat）
- 提交信息：必须写清楚干了两种活，例如：

```
重构心情记录模块并新增宠物喂养接口

- refactor: 将心情记录模块的 Service 层逻辑拆分，消除重复代码
- feat: 新增宠物喂食接口 /api/pet/feed
```

## 3. 提交信息规范

- 提交信息使用中文。
- 首行写一句概括，正文分条列出本次实际完成的工作（涉及多种类型时逐条标注类型）。
- 提交前确认代码可以正常编译，涉及接口改动时需通过接口测试验证。

## 4. 分层与命名规范

代码统一放在 `org.example.lifeandmood` 包下，按层分包：

```
org.example.lifeandmood
├── controller   # 接口层：接收请求、返回响应，不写业务逻辑
├── service      # 业务层：接口 + 实现（实现类放 service.impl 子包）
│   └── impl
├── mapper       # 数据访问层：MyBatis-Plus Mapper 接口
├── po           # 持久层对象：与数据库表一一对应
├── dto          # 数据传输对象：接收前端请求参数
└── vo           # 视图对象：返回给前端的数据
```

### 命名规则

以表 `share_post`（数据库名，下划线转大驼峰 `SharePost`）为例：

| 层 | 命名规则 | 类名示例 | 所在包 |
| --- | --- | --- | --- |
| PO | 数据库表名（大驼峰），**不加后缀** | `SharePost` | `po` |
| DTO | 表名 + `DTO` | `SharePostDTO` | `dto` |
| VO | 表名 + `VO` | `SharePostVO` | `vo` |
| Mapper | 表名 + `Mapper` | `SharePostMapper` | `mapper` |
| Service | 表名 + `Service` | `SharePostService` | `service` |
| Service 实现 | 表名 + `ServiceImpl` | `SharePostServiceImpl` | `service.impl` |
| Controller | 表名 + `Controller` | `SharePostController` | `controller` |

说明：

- 所有类名使用大驼峰；表名中的下划线去掉、每个单词首字母大写（`pet_care_log` → `PetCareLog`）。
- PO 与表一一对应，字段名与数据库列名保持一致（MyBatis-Plus 自动映射下划线 ↔ 小驼峰）。
- DTO 用于接收请求参数，VO 用于返回响应，二者都要加后缀；PO 不加任何后缀，直接用表名。

## 5. 类注释模板

创建任何类（PO、DTO、VO、Mapper、Service、Controller 等）必须使用以下类注释模板，放在类声明上方：

```java
/**
@Author: ICERainbow666
@Package: ${PACKAGE_NAME}
@Project: ${PROJECT_NAME}
@ClassName: ${NAME}
@Date: ${DATE} ${TIME}
@FileEffect: 描述该文件的作用（可根据自己内容填写）
*/
```

其中 `@FileEffect` 必须替换为该文件的实际作用描述，其余变量由 IDEA 自动填充。

### IDEA 配置方法

`Settings → Editor → File and Code Templates → Files → Class`，在模板顶部加入上方注释内容（模板变量 IDEA 会自动解析）。配置一次后，新建类会自动生成，团队成员请统一使用该配置。

## 6. Controller / Service 分工与类型规范

### 分工红线

- **Controller 不写业务逻辑**：只负责接收参数、调用 Service、返回结果，校验以外的逻辑一律放 Service。
- **Service 禁止把 PO 直接返回给前端**：PO 是数据库表的映射，只允许在 Service 层内部流转；返回给 Controller/前端的必须是 VO，由 Service 完成转换。分层不转层等于白分。
- **事务**：一次操作涉及多张表写入时，Service 方法必须加 `@Transactional`，且加在 Service 实现类上。

### 类型使用规范

| 数据 | 必须使用 | 禁止使用 | 对应数据库类型 | 项目示例 |
| --- | --- | --- | --- | --- |
| 金额 | `BigDecimal` | `double` / `float` | `DECIMAL` | `transaction.amount`、`budget.amount` |
| 纯日期 | `LocalDate` | `Date`、`String` 存日期 | `DATE` | `record_date`、`diary_date` |
| 日期+时间 | `LocalDateTime` | `Date`、`Timestamp` | `DATETIME` | `created_at`、`updated_at` |

说明：

- `BigDecimal` 禁止用 `new BigDecimal(0.1)` 这种 double 构造（有精度问题），用字符串构造 `new BigDecimal("0.1")` 或 `BigDecimal.valueOf()`；比较大小用 `compareTo()`，不用 `equals()`。
- 日期时间的类型在 PO、DTO、VO 中保持一致，禁止为了图省事用 `String` 接日期再自己转。
- 对应关系：`DATE` 列 ↔ `LocalDate`，`DATETIME` 列 ↔ `LocalDateTime`，写代码前先看 `docs/数据库设计.md` 里该列的类型。
